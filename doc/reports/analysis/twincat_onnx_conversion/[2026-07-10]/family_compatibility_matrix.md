# TwinCAT ONNX Family Compatibility Matrix

## Summary

The TwinCAT ONNX conversion pipeline was tested against one representative ONNX
export from each of the 37 implemented model families listed in the
dataset-input-mode retraining technical plan.

Final evidence is stored under:

```text
output/deployment/twincat_onnx_conversion/family_matrix_20260710_shape_fixed/
```

The final matrix result is:

- 37 / 37 families have a representative ONNX export.
- 37 / 37 families complete the `TF3820` `onnxprep` route and produce
  Machine Learning Server JSON plus PLCopen XML artifacts.
- 2 / 37 families complete the current `TF38x0` XML/BML route:
  `rcim_track1` and `tree`.
- 35 / 37 families require the `TF3820` route unless a dedicated
  `TF38x0`-friendly model variant is trained or exported.

## Feedforward Finding

The feedforward representative is:

```text
models/polished_dataset/actual_values/exported/feedforward/forward/2026-07-07-18-43-03__te_feedforward_fw__polished_actual_values/onnx/model.onnx
```

ONNX checker and ONNX Runtime smoke inference pass. `TF38x0` fails because the
export contains operators and scalar constants generated by `LayerNorm` and
`GELU`. Experiments showed:

- scalar `Constant` nodes can be normalized to one-dimensional constants
  without changing ONNX Runtime outputs;
- re-exporting at opset 16 decomposes `LayerNormalization`;
- the decomposed graph still requires `ReduceMean`, which Beckhoff `TF38x0`
  MLlib 3.1.251201.0 does not implement.

Therefore the existing feedforward checkpoint is not safely convertible to the
current `TF38x0` XML/BML runtime through ONNX post-processing alone. It is,
however, accepted by the `TF3820` `onnxprep` path after the converter fix for
in-place preparation.

## Pipeline Changes

The converter now handles the current Beckhoff `onnxprep` behavior correctly:

- the `TF3820` route copies the ONNX into the route-local `tf3820/` directory;
- `onnxprep` is called with the input path only, because this toolbox build
  writes companion files next to the input;
- generated `model.json` and `model_plcopen.xml` paths are captured in the
  conversion manifest.

The converter also supports:

```text
--freeze-nonbatch-dynamic-dims
```

This option freezes dynamic input or output dimensions after axis `0` on the
run-local ONNX copy. It is required for sequence models because `TF3820`
accepts an unknown leading batch dimension but rejects later dynamic dimensions
such as `sequence_length`. When a model archive includes
`training_config.snapshot.yaml`, the converter uses its `sequence_length`; for
the tested sequence families this resolves to `33`.

## Compatibility Result

| Family group | Result |
| --- | --- |
| `rcim_track1`, `tree` | Compatible with `TF38x0` XML/BML and `TF3820`. |
| Dense, harmonic, periodic, temporal, recurrent, Wave 3, Wave 4, and Wave 5 neural families | Compatible with `TF3820` JSON plus PLCopen XML after local shape freezing where required. |
| Existing non-tree neural exports | Not compatible with the current `TF38x0` XML/BML route without model/export redesign. |

## Deployment Interpretation

For the current TestRig PLC code path based on `TF38x0`,
`Tc3_MLL.FB_MllPrediction`, XML, and BML, use only representatives that pass
the `TF38x0` route.

For all current neural families, the practical path is to evaluate switching
the PLC integration to `TF3820` Machine Learning Server artifacts:

```text
ONNX -> onnxprep -> JSON + PLCopen XML -> FB_MlSvrPrediction
```

If `TF38x0` must remain mandatory for the online compensation path, the neural
families need dedicated deployment variants trained without importer-hostile
normalization/reduction operators.
